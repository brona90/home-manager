# Editing a Nix-managed home

Almost every dotfile on these machines is a read-only symlink into `/nix/store`,
generated from a flake. The failure this skill prevents is quiet: you edit the
file you can see, the edit appears to work, and then it is erased by the next
rebuild — or it never reaches the other two machines at all.

Check before you edit:

```sh
ls -l <file>          # a /nix/store symlink means Nix owns it
```

If it is a symlink into the store, the file is an *output*. Find the input.

## Where the inputs live

| Output you can see | Input you edit |
|---|---|
| `~/.claude/settings.json` | `modules/claude-code.nix` (the `settings` let-binding) |
| `~/.claude/CLAUDE.md` | assembled from `my.claudeCode.claudeMdSections`; each module contributes one |
| `~/.claude/commands/`, `~/.claude/templates/specflow/` | `modules/claude-specflow/` |
| `~/.claude/skills/`, `~/.claude/agents/` | `modules/claude-skills/` |
| `~/.config/emacs/` — the Emacs config | `modules/emacs/vanilla/config/{early-init,init}.el` and `config/lisp/*.el`; its package list is `modules/emacs/vanilla/package.nix`. Run `bash modules/emacs/vanilla/verify.sh` after changing it |
| `lisp/my-nix-paths.el` in the built config | **generated by `package.nix` at build time**, not a source file. It carries store paths the elisp must not hardcode. It is not in git; `require`d with `noerror`, so read its variables with `bound-and-true-p` |
| shell aliases, git, gpg, tmux | `modules/{zsh,git,gpg,tmux}.nix` |
| MCP servers | `my.claudeCode.mcpServers`, merged into `~/.claude.json` on activation |

The repo is `~/.config/home-manager` (remote `github.com:brona90/home-manager`).
Worktrees for in-flight branches sit beside it, e.g. `~/.config/hm-claude-plugins`.
Check `git worktree list` before starting a branch — the one you want may exist.

MCP servers are deliberately *not* in `settings.json`; Claude Code ignores
`mcpServers` there and reads user-scope servers only from the mutable
`~/.claude.json`, so the module merges into that file during activation instead
of owning it.

## Rebuilding

```sh
hms      # home-manager switch --flake ~/.config/home-manager#gfoster@x86_64-linux -b backup
```

Validate without switching — this is the cheap loop, and it runs the same
`writeShellApplication` shellcheck that a switch would:

```sh
nix build ~/.config/home-manager#home-gfoster --no-link
nix flake check
```

**`git add` any new file before you build.** Flakes only see git-tracked files,
so an untracked module or `.el` is absent from the store — and the build either
succeeds while ignoring your change or fails with an error that names the
`require`, not the missing `git add`.

After a rebuild the Emacs daemon keeps running the old build ("Keeping old
units"): home-manager sets `X-RestartIfChanged = false` on the `emacs` unit so
`hms` can never eat unsaved buffers. Loading the new profile needs
`systemctl --user restart emacs.service`, which drops open buffers — so mention
it rather than doing it unasked.

There is exactly one Emacs unit. A second one, `emacs-doom`, existed while Doom
was being retired; if it is still present on a machine it is a leftover from an
older generation — see `modules/emacs/RETIRING-DOOM.md`.

Emacs config changes have their own gate, and it is not optional: run
`bash modules/emacs/vanilla/verify.sh`. `package-enable-at-startup` is nil in
that config, so a key can be bound, show a name in the which-key popup, and be
**void** when pressed; nothing short of starting a real daemon catches it.

## Gates

Pre-commit runs `statix`, `deadnix`, `alejandra`, `shellcheck` — run `alejandra`
on any `.nix` file you touch or the commit will bounce.

**Get the linters from this flake, not from the registry.** `lib/lint-tools.nix`
is exposed as `packages.<system>.lint-tools`; `nix run nixpkgs#shellcheck`
resolves through the *machine's* registry and gave CI and a laptop two different
versions (a renumbered shellcheck finding turned a green local run red in CI).
Check each linter by **exit code** — a linter that cannot be resolved is a
failure, never a skip:

```sh
nix build '.#lint-tools' --no-link
```

**Touching `modules/emacs/vanilla` means running the Emacs gate**, which no
other command covers:

```sh
bash modules/emacs/vanilla/verify.sh
```

It lints, builds, then starts a **real daemon** from the store config directory
and asserts against it. `emacs --batch` does not load `init.el` at all, so a
batch check reports success having loaded nothing — that is how six leader keys
once shipped bound to void commands with every CI job green. Its stage 0 also
catches the trap that a new `lisp/*.el` which has not been `git add`ed is simply
absent from the store, and fails as "Cannot open load file".

`nix flake check` also runs **guards**: regression tests that assert invariants
which were once broken for real. A guard failing means you reintroduced a known
bug — work out what it was protecting before you touch the guard itself.

| Guard | Asserts |
|---|---|
| `claude-settings-guards` | `settings.json` keeps `attribution = {commit = ""; pr = "";}`, and `mcp__emacs__emacs_eval` is never auto-allowed (arbitrary elisp is arbitrary shell, and it would bypass every other permission gate) |
| `docker-terminal-no-ssh-mount` | `~/.ssh` is never bind-mounted into the docker terminal |
| `ci-emacs-gate` | `build-home` has no job-level `if` (that is what made it skip on every PR), exactly one of its steps runs `verify.sh`, and nothing in `ci.yml` runs Emacs with `--batch` |
| `lint-tools-pinned` | no lint step and no line of `verify.sh` resolves a tool through `nixpkgs#`, and `verify.sh` never uses `--impure` |
| `devshell-stays-light` | `devShells.default` re-runs neither the git-hooks installer nor the linters — both were on the `cd` path and cost ~43 s |
| `install-hooks-installs-hooks` | the wrapped installer is really git-hooks.nix's, `install-hooks.sh` can repair a deleted `pre-commit` hook, and the warm hooks stay GC-rooted |
| `background-jobs-close-fds` | no shipped script backgrounds a job while holding inherited descriptors |
| `devshell-hook-lint` | the shellHook stays lint-clean |
| `tmux-helper-build`, `tmux-helper-vet` | the Go helper builds and `go vet` passes |

There is no pre-push `nix flake check` — it held the connection open long enough
that GitHub dropped the push. CI runs it instead.

**In a fresh worktree the `pre-commit` hook aborts.** `.git/hooks` is shared by
every worktree, but `.pre-commit-config.yaml` is a gitignored symlink
materialised per working directory — so a worktree you have never `cd`ed into
with direnv active has the hook but not its config, and every commit fails with
"No .pre-commit-config.yaml file was found". Fix it properly by entering the
directory so the shellHook runs, or:

```sh
nix run .#install-hooks
```

The hook set is exactly `statix`, `deadnix`, `alejandra`, `shellcheck`
(`lib/pre-commit-hooks.nix`), so if you have already run those four by exit code
you have run the gate — but say so rather than silently passing
`PRE_COMMIT_ALLOW_NO_CONFIG=1`, which makes an unlinted commit look linted.

## Committing

**You cannot commit here.** Commits are GPG-signed by a YubiKey forwarded from
Windows Gpg4win, which needs an interactive PIN and a physical touch. Stage the
work, then hand Gregory the exact command to run.

The default branch is `master`, not `main`.

Do not add `Co-Authored-By` or "Generated with Claude Code" trailers: the managed
`settings.json` sets `attribution.commit` and `attribution.pr` to empty strings
precisely so they never appear, and a guard enforces it. (Claude Code running
natively on Windows reads a *different*, hand-maintained `settings.json` that
does not yet set this — so check which side you are on before writing a commit
message.)

## Traps

- `~/.config/emacs/` is **live, managed config** — the Emacs tree, linked
  from `modules/emacs/vanilla/config/` by `xdg.configFile."emacs"`
  (`recursive = true`, so the directory stays writable). It is an output: edit
  the module. On a machine that has not switched in a long time it may still
  hold the pre-Nix doomemacs checkout, which `hms -b backup` moves aside.
- `~/.config/doom/` and `~/.local/share/nix-doom/` are leftovers: Doom was
  retired and nothing in the flake references either. They look like config and
  have no effect. Deleting them is a manual step —
  `modules/emacs/RETIRING-DOOM.md`.
- `~/.config/nvim/`, `~/.local/share/nvim/`, `~/.local/state/nvim/` and
  `~/.cache/nvim/` are the same class: LazyVim was removed and `modules/vim/`
  no longer exists, so nothing in the flake references any of them. The `vcc`
  alias that used to clear them went with it. `~/.local/share/nvim` is the big
  one (plugin copies plus an orphaned `mason/` tree). Removing it needs
  `chmod -R u+w` first: the plugins were `cp`d out of the read-only store and
  their directories have no write bit, so `rm -rf` fails partway.
- Never hardcode a `/nix/store/<hash>/` path into anything outside the flake —
  the hash changes on every rebuild. Use the stable wrappers in
  `~/.nix-profile/bin/` (`kg-server`, `searxng-mcp`, `emacs-mcp-server`).
- `config.local.nix` merges over `config.nix` with `recursiveUpdate`: nested
  attrsets merge key-by-key, but **lists and scalars replace wholesale**.
- Secrets are sops-nix (`secrets/secrets.yaml`, age key at
  `~/.config/sops/age/keys.txt`), decrypted to `~/.config/sops-nix/secrets/`.
  Rotate non-interactively with `sops set`, which preserves the age recipients:
  ```sh
  SOPS_AGE_KEY_FILE=~/.config/sops/age/keys.txt \
    sops set secrets/secrets.yaml '["group"]["key"]' '"value"'
  ```
